# FuelLead — состояние проекта

Дата актуализации: 2026-08-31

## Изменения текущей итерации

- Кнопки «Экспорт» на экранах «Обзор» и «Компании» заменены кнопкой
  «Отправить письма». Excel endpoint сохранён для обратной совместимости, но больше не
  является основным действием интерфейса.
- Реализована сохраняемая PostgreSQL-очередь писем с предпросмотром выборки,
  обязательным подтверждением, прогрессом, паузой, продолжением и отменой остатка.
- В очередь допускаются только действующие компании со статусом `ready`; выбирается
  один основной email на компанию, исключаются одинаковые и ранее использованные адреса.
- По умолчанию один запуск и день ограничены 20 адресатами, час — пятью письмами,
  интервал — минимум пятью минутами, один домен — двумя письмами в сутки. Ограничения
  применяются backend и не снимаются через UI.
- Тема и текст персонализируются и фиксируются при создании очереди. Каждое письмо
  содержит видимый текст отказа, `Message-ID` и `List-Unsubscribe: mailto`.
- Ошибка/ограничение Gmail ставит очередь на паузу. Неоднозначная отправка при
  перезапуске помечается ошибкой без автоматического повтора, чтобы не создать дубль.
- Одиночная быстрая отправка теперь использует только основной email компании и
  подчиняется тем же дневным, часовым, доменным и интервальным ограничениям.
- Добавлены автотесты eligibility, дедупликации, снимка шаблона, успешного worker-tick,
  паузы на Gmail 429, ожидания интервала и восстановления после прерывания. Реальные
  письма при проверке этой итерации не отправлялись.

- Добавлен третий discovery-провайдер `api_fns`; выбор выполняется через
  `DISCOVERY_PROVIDER=api_fns|checko|combined|demo`. Режим `auto` сохраняет прежнее поведение для
  существующих локальных конфигураций: Checko при наличии его ключа, иначе demo.
- Добавлен режим `combined`: одна кнопка последовательно запускает Checko, затем API-ФНС;
  ошибка или исчерпание Checko не блокирует второй этап. Курсоры `discovery_cursors` теперь
  разделены по провайдеру, а существующие позиции сохранены как позиции Checko.
- Реализованы отдельные клиент и парсер API-ФНС для `/search`, `/egr` и `/stat`.
  Поиск передаёт `active`, `onlyul`, основной ОКВЭД и один регион (`77` или `50`),
  поддерживает страницы и опциональные фильтры `withphone`/`withemail`.
- API-ФНС документирован и реализован только как поиск по **основному ОКВЭД**.
  Дополнительные ОКВЭД читаются из карточки `egr`, но не считаются критерием найденной выборки.
- Общий discovery использует общую таблицу `discovery_cursors` с отдельной позицией для
  каждого провайдера и по-прежнему отсеивает известные/исключённые ИНН до запроса полной карточки.
- Карточка API-ФНС повторно проверяется на действующий статус и регион `77`/`50`; название,
  ИНН, ОГРН, основной/дополнительные ОКВЭД, телефоны и email сохраняются через существующий upsert.
- Добавлены безопасные сообщения для неверного ключа, исчерпания лимита, ограничения IP,
  rate limit, сетевого тайм-аута и неподдерживаемого ответа без вывода ключа или полного URL.
- Один запуск API-ФНС по умолчанию ограничен суммарно пятью `search` и пятью `egr`
  независимо от количества ОКВЭД; при достижении cap курсор сохраняется, а UI получает
  предупреждение. Лимиты повышаются только отдельными переменными конфигурации.
- `/api/health` теперь сообщает выбранного провайдера, наличие настройки API-ФНС,
  конфигурационное состояние Checko, регионы и лимит поиска, не раскрывая секреты.
- Добавлена команда `python -m app.commands.check_api_fns`: два `/stat`, максимум один
  `search` и один `egr`, только агрегированные поля в выводе. Режим `--stat-only` получает
  расход по `search/egr` одним `/stat` без вызова этих методов. Мок-тест подтверждает точное
  число вызовов и отсутствие ключа в выводе.
- Первая live-проверка не состоялась: локальный хост устанавливает TCP-соединение с
  `api-fns.ru`, но TLS-handshake стабильно завершается timeout даже для публичной
  `/api_help`. HTTP-запросы `search/egr` до сервиса не дошли, расход подтверждён как
  `0 search / 0 egr`; фактический контракт нужно проверить вручную после восстановления HTTPS.
- После настройки разрешённого IP ручная smoke-проверка API-ФНС завершилась успешно:
  `search` по основному ОКВЭД `49.41` и региону `50` вернул 100 записей и 3 страницы,
  `egr` вернул действующую карточку с регионом `50`, основным ОКВЭД `49.41`, телефонами
  и email. Статистика показала расход `1 search` и `1 egr`.
- После smoke-проверки из интерфейса выполнено 20 запусков API-ФНС: 19 завершились с
  сохранением 85 новых компаний, один остановился из-за ограничения IP. Последующий
  безопасный `--stat-only` также получил отказ, поскольку исходящий IP снова изменился;
  точный остаток лимита нужно сверять после фиксации стабильного IP.

- В карточку компании добавлены отдельные способы связи: телефон, WhatsApp и Telegram.
  Телефоны автоматически читаются из `Контакты → Тел` Checko для новых карточек;
  любой из трёх типов можно добавить вручную с нормализацией и проверкой формата.
- Контакты отображаются в таблице и раскрытой карточке как кликабельные `tel:`, `wa.me`
  и `t.me` ссылки. Ручные контакты можно удалить; контакты Checko защищены от ручного

- Сводка способов связи в строке таблицы ограничена первыми тремя значениями: для компаний
  с большим числом email и телефонов показывается компактная кнопка `Ещё N`, раскрывающая
  карточку с полным списком. Это устраняет чрезмерную высоту строк на desktop и mobile.
- Реализовано удаление компании вместе с email, контактами, ОКВЭД и историей. ИНН

## Текущая цель

Оценить качество первой реальной выборки выбранного провайдера и подготовить discovery-поток к регулярному внутреннему использованию:

1. поиск действующих организаций: API-ФНС — только по основному ОКВЭД, Checko — по основным и дополнительным;
2. получение карточек компаний и доступных email;
3. сохранение и дедупликация в PostgreSQL;
4. отображение, фильтрация, смена статуса и история действий;
5. экспорт результата в `.xlsx`;
6. сохранение данных после перезапуска приложения;
7. снижение шума по дополнительным ОКВЭД и обработка временных сетевых ошибок.

Поиск сайтов, полноценная CRM, AI-скоринг и поиск сотрудников не входят в текущий MVP.
Email-очередь добавлена как ограниченный внутренний инструмент только для вручную
проверенных компаний со статусом «Готова».

## Завершённые задачи

### Интеграция API-ФНС

- Реализован клиент `ApiFnsClient` с безопасными `/search`, `/egr`, `/stat`.
- Поиск использует `q=any`, `active`, `onlyul`, `okved<код>`, `region<код>` и `page`.
- `withphone` и `withemail` включаются раздельно через конфигурацию и по умолчанию выключены.
- Парсер карточки читает `Адрес.КодРегион`, `ОснВидДеят`, `ДопВидДеят`,
  `Контакты.Телефон` и `Контакты.e-mail`, нормализует и дедуплицирует контакты.
- Размер страницы API-ФНС принят равным 100 согласно документации; `filter_any_count` и
  `nextpage` используются для продвижения курсора.
- Настроены предохранители `API_FNS_MAX_SEARCH_REQUESTS_PER_RUN=5` и
  `API_FNS_MAX_EGR_REQUESTS_PER_RUN=5`.
- Неизвестные/исключённые ИНН пропускаются до `egr`; полный ответ снова проверяется на
  действующий статус и целевой регион перед записью в PostgreSQL.
- В режиме `combined` API-ФНС запускается после завершения этапа Checko и использует собственный
  курсор, поэтому не повторяет позиции Checko.

### Интеграция Checko

- Реализован клиент Checko API v2.
- Поиск выполняется через `/search` с `by=okved`, `obj=org`, `active=true`, `codes=all`
  отдельно для `region=77` и `region=50`.
- Поддерживаются основной и резервные API-ключи; исчерпанный или отклонённый ключ
  исключается до конца запуска, а запрос продолжается со следующим ключом.
- `codes=all` включает поиск по основным и дополнительным ОКВЭД.
- Полная карточка запрашивается через `/company` по ИНН.
- Перед сохранением код региона полной карточки обязательно проверяется повторно.
- Парсятся статус, название, ИНН, ОГРН, основной ОКВЭД, дополнительные ОКВЭД,
  `Контакты → Емэйл` и `Контакты → Тел`.
- Невалидные email отбрасываются, остальные нормализуются и дедуплицируются.
- При отсутствии ключа предусмотрен отдельный демонстрационный режим.
- В режиме `combined` Checko всегда является первым этапом, после которого запускается API-ФНС;
  лимиты провайдеров не смешиваются.

### Хранение и бизнес-логика

- PostgreSQL является основной контейнерной базой.
- Подключение к базе и Checko настраивается переменными окружения.
- ИНН имеет уникальное ограничение и используется для дедупликации компаний.
- Email уникален в пределах компании.
- Телефон, WhatsApp и Telegram уникальны в пределах компании и типа контакта.
- Удалённые вручную компании сохраняются в стоп-листе по ИНН и не обнаруживаются повторно.
- Поддерживаются ноль, один и несколько email.
- Хранятся `first_discovered_at`, `last_checked_at`, `last_updated_at`.
- Реализованы MVP-статусы `new`, `checked`, `ready`.
- Модель допускает будущие статусы outreach без включения рассылки в MVP.
- История фиксирует обнаружение, получение/обновление данных, новый email и смену статуса.
- Категория деятельности определяется сначала по основному целевому ОКВЭД, затем по дополнительным кодам.
- Фоновый запуск поиска и его счётчики сохраняются в `search_runs`.
- Повторяющиеся дополнительные ОКВЭД в одной карточке Checko дедуплицируются до записи в базу.
- Позиция поиска хранится по каждой паре «ОКВЭД + регион» и переживает перезапуск backend.
- Известные компании пропускаются до запроса полной карточки; discovery продвигается по страницам, а не
  обновляет одни и те же записи при каждом ручном запуске.
- Незавершённые `pending`/`running`-запуски при старте backend переводятся в `failed` с явной причиной вместо вечного зависания.

### API и экспорт

- `GET /api/health` — выбранный discovery-провайдер и безопасное состояние его конфигурации.
- `GET /api/companies` — список, пагинация, статистика и фильтры.
- `GET /api/companies/{id}` — подробная карточка, дополнительные ОКВЭД и история.
- `PATCH /api/companies/{id}/status` — смена статуса.
- `POST /api/companies/{id}/contacts` — добавление контакта.
- `DELETE /api/companies/{id}/contacts/{contact_id}` — удаление ручного контакта.
- `DELETE /api/companies/{id}` — удаление компании с помещением ИНН в стоп-лист.
- `POST /api/search-runs` — запуск поиска.
- `GET /api/search-runs/{id}` — состояние поиска.

### Интерфейс

- Реализован React + TypeScript + Vite frontend.
- Есть сводка: всего, новые, с email, без email.
- Есть фильтры по статусу, наличию email, категории, дате, названию и ИНН.
- В раскрытой карточке можно добавить телефон, WhatsApp или Telegram и удалить ручной контакт.
- Удаление фирмы требует подтверждения и объясняет, что ИНН попадёт в стоп-лист.
- Работают раскрытие карточки, история, смена статуса, поиск и пагинация.
- Табличный desktop-интерфейс адаптируется в читаемый мобильный список.
- Nginx раздаёт frontend и проксирует `/api/` в backend.

## Ключевые технические решения

- Backend: Python 3.12, FastAPI, SQLAlchemy 2, Pydantic Settings, HTTPX.
- Database: PostgreSQL 17, `psycopg` 3; SQLite используется только для локальных тестов/демо-разработки вне Docker.
- Frontend: React 19, TypeScript, Vite, Lucide icons.
- Export: `openpyxl`.
- Запуск: Docker Compose, отдельные контейнеры PostgreSQL, backend и frontend.
- UI и API работают с одного frontend origin через Nginx proxy.
- Схема базы на текущем MVP создаётся через `SQLAlchemy.metadata.create_all()` при старте backend.
- Поиск выполняется через FastAPI `BackgroundTasks`; отдельная очередь задач пока не используется.

## Известные проблемы и ограничения

1. Live-контракт API-ФНС пока не подтверждён с этого компьютера: TLS-handshake к
   `api-fns.ru:443` завершается timeout до передачи HTTP-запроса. Клиент и парсер проверены
   только по официальной документации, примерам ответа и мокам.
2. По контексту текущей итерации все три Checko-ключа возвращают HTTP 401 «API-ключ не
   действителен», а штатная вкладка API в кабинете ведёт на 404. Checko оставлен как
   переключаемый режим, но его работоспособность сейчас не подтверждена.
3. API-ФНС документирует фильтрацию только по основному ОКВЭД. Компании по дополнительным
   ОКВЭД этим провайдером не обнаруживаются; дополнительные коды только сохраняются из `egr`.
4. Существующие курсоры сохраняются и переводятся в 100-записную страницу API-ФНС по
   абсолютному смещению, но порядок результатов разных провайдеров не обязан совпадать.
   После переключения нужна ручная проверка первой небольшой выборки.
5. `search_runs` хранит агрегированные счётчики и последнюю ошибку, но не отдельный
   результат по каждому ОКВЭД. Per-run cap API-ФНС отображается как предупреждение.
6. Автоматический retry/backoff для временных сетевых ошибок не добавлен: API-ФНС безопасно
   останавливает текущий запуск, чтобы неопределённый timeout не расходовал лимит повторно.
7. Схема базы создаётся через `create_all`; версионируемых миграций Alembic пока нет.
8. `BackgroundTasks` не является надёжной очередью: незавершённый поиск прервётся при
   перезапуске backend, будет помечен `failed`, но автоматически не возобновится.
9. Сессия авторизации stateless и не имеет серверного списка отзыва: выход удаляет cookie
   текущего устройства, а для отзыва всех сессий нужно сменить секрет или пароль.
10. Порт PostgreSQL опубликован на хосте для разработки. В постоянном окружении его следует
    закрыть от внешней сети.
11. Контактные данные провайдеров могут отсутствовать или быть устаревшими; наличие email
    не подтверждает релевантность или согласие на рекламу.
12. Уже сохранённые компании не запрашиваются повторно ради backfill контактов, чтобы не
    расходовать лимит. Для них контакты добавляются вручную или отдельным будущим процессом.
13. Интерфейса просмотра и восстановления внутреннего стоп-листа пока нет.
14. Рабочие изменения текущей итерации не закоммичены и не отправлены в Git.
15. Локальный файл `логины_пароли.xlsx` удалён из текущего Git index и добавлен в
    `.gitignore`, но остаётся в истории. Перед публикацией историю нужно очистить, а ранее
    сохранённые там секреты — ротировать.

## Опробованные подходы, которые не сработали

- Docker build backend периодически завершался из-за тайм-аутов доступа к PyPI при
  скачивании зависимостей; код приложения причиной ошибок не был. В Dockerfile увеличены
  timeout и число retry для `pip`.
- Первая пересборка контейнеров после добавления авторизации получила временный TLS
  handshake timeout Docker Hub; повтор без принудительного pull завершился успешно.
- Открытие `0.0.0.0:8000` как пользовательского интерфейса приводило к `Not Found`. Это адрес прослушивания backend, а не frontend URL.
- Старый локальный Uvicorn на `127.0.0.1:8000` перехватывал локальные проверки и показывал demo/SQLite-состояние вместо Docker. Процесс остановлен; текущий порт обслуживает Docker-backend с Checko и PostgreSQL.
- Первый live-запуск остановился на карточке с повторяющимся дополнительным ОКВЭД: PostgreSQL отклонил дубль, а SQLAlchemy-сессия не смогла сохранить финальный статус. Парсер и upsert теперь дедуплицируют коды, запись компании выполняется в savepoint, а прерванный запуск закрывается при старте backend.
