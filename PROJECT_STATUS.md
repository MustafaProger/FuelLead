# FuelLead — состояние проекта

Дата актуализации: 2026-08-27

## Изменения текущей итерации

- Подтверждена причина `403`: бесплатный тариф Checko исчерпал суточный лимит
  100 запросов при нулевом балансе; формат запроса приложения корректен.
- Checko-ошибки переводятся в безопасные пользовательские сообщения без API-ключа
  и сырого URL. При исчерпании лимита перебор ОКВЭД прекращается после первого ответа.
- Старые сообщения поисковых запусков с `key=...` очищаются при старте backend и
  дополнительно редактируются при сериализации API.
- В `.env` исправлен адрес frontend API: кириллическое `/apiа` заменено на `/api`.
- Отправителем рассылки зафиксирован `artel.office8@gmail.com`; подготовлен сервис
  Gmail API OAuth 2.0 без пароля приложения. Массовая отправка ещё не активирована.
- Интерфейс переработан по правилам установленного `apple-design`: системная
  типографика, материальные поверхности, мгновенная обратная связь, понятные состояния,
  адаптивный mobile-список и режимы reduced motion/transparency/contrast.

## Текущая цель

Оценить качество первой реальной выборки Checko и подготовить discovery-поток к регулярному внутреннему использованию:

1. поиск действующих организаций по основным и дополнительным ОКВЭД;
2. получение карточек компаний и доступных email;
3. сохранение и дедупликация в PostgreSQL;
4. отображение, фильтрация, смена статуса и история действий;
5. экспорт результата в `.xlsx`;
6. сохранение данных после перезапуска приложения;
7. снижение шума по дополнительным ОКВЭД и обработка временных сетевых ошибок.

Email-рассылка, поиск сайтов, CRM, AI-скоринг и поиск сотрудников не входят в текущий MVP.

## Завершённые задачи

### Интеграция Checko

- Реализован клиент Checko API v2.
- Поиск выполняется через `/search` с `by=okved`, `obj=org`, `active=true`, `codes=all`.
- `codes=all` включает поиск по основным и дополнительным ОКВЭД.
- Полная карточка запрашивается через `/company` по ИНН.
- Парсятся статус, название, ИНН, ОГРН, основной ОКВЭД, дополнительные ОКВЭД и `Контакты → Емэйл`.
- Невалидные email отбрасываются, остальные нормализуются и дедуплицируются.
- При отсутствии ключа предусмотрен отдельный демонстрационный режим.

### Хранение и бизнес-логика

- PostgreSQL является основной контейнерной базой.
- Подключение к базе и Checko настраивается переменными окружения.
- ИНН имеет уникальное ограничение и используется для дедупликации компаний.
- Email уникален в пределах компании.
- Поддерживаются ноль, один и несколько email.
- Хранятся `first_discovered_at`, `last_checked_at`, `last_updated_at`.
- Реализованы MVP-статусы `new`, `checked`, `ready`.
- Модель допускает будущие статусы outreach без включения рассылки в MVP.
- История фиксирует обнаружение, получение/обновление данных, новый email и смену статуса.
- Категория деятельности определяется сначала по основному целевому ОКВЭД, затем по дополнительным кодам.
- Фоновый запуск поиска и его счётчики сохраняются в `search_runs`.
- Повторяющиеся дополнительные ОКВЭД в одной карточке Checko дедуплицируются до записи в базу.
- Незавершённые `pending`/`running`-запуски при старте backend переводятся в `failed` с явной причиной вместо вечного зависания.

### API и экспорт

- `GET /api/health` — состояние приложения и конфигурации Checko.
- `GET /api/companies` — список, пагинация, статистика и фильтры.
- `GET /api/companies/{id}` — подробная карточка, дополнительные ОКВЭД и история.
- `PATCH /api/companies/{id}/status` — смена статуса.
- `POST /api/search-runs` — запуск поиска.
- `GET /api/search-runs/{id}` — состояние поиска.
- `GET /api/export.xlsx` — Excel-выгрузка текущей выборки.

### Интерфейс

- Реализован React + TypeScript + Vite frontend.
- Есть сводка: всего, новые, с email, без email.
- Есть фильтры по статусу, наличию email, категории, дате, названию и ИНН.
- Работают раскрытие карточки, история, смена статуса, поиск и пагинация.
- Табличный desktop-интерфейс адаптируется в читаемый мобильный список.
- Nginx раздаёт frontend и проксирует `/api/` в backend.

## Ключевые технические решения

- Backend: Python 3.12, FastAPI, SQLAlchemy 2, Pydantic Settings, HTTPX.
- Database: PostgreSQL 17, `psycopg` 3; SQLite используется только для локальных тестов/демо-разработки вне Docker.
- Frontend: React 19, TypeScript, Vite, Lucide icons.
- Export: `openpyxl`.
- Запуск: Docker Compose, отдельные контейнеры PostgreSQL, backend и frontend.
- UI и API работают с одного frontend origin через Nginx proxy.
- Схема базы на текущем MVP создаётся через `SQLAlchemy.metadata.create_all()` при старте backend.
- Поиск выполняется через FastAPI `BackgroundTasks`; отдельная очередь задач пока не используется.

## Известные проблемы и ограничения

1. В одном live-запуске три запроса Checko получили временный SSL handshake timeout. Обработка продолжилась по следующим кодам, но автоматического retry/backoff пока нет.
2. Запуск со смесью успешных результатов и ошибок получает статус `completed`, однако интерфейс показывает только созданные/обновлённые записи и не выводит `errors_count` как предупреждение.
3. Первая выборка показывает заметный шум при `codes=all`: организация может попасть в результат из-за дополнительного ОКВЭД, хотя основной вид деятельности не выглядит целевым. Требуется ручная оценка 20–50 компаний и статистика качества по исходному коду поиска.
4. `search_runs` хранит общий счётчик и последнее сообщение об ошибке, но не сохраняет результат и ошибку отдельно по каждому ОКВЭД.
5. Схема базы создаётся через `create_all`; версионируемых миграций Alembic пока нет.
6. `BackgroundTasks` не является надёжной очередью: незавершённый поиск прервётся при перезапуске backend. Теперь такой запуск корректно помечается `failed`, но автоматически не возобновляется.
7. В MVP нет авторизации пользователей. Перед постоянным внутренним размещением требуется ограничить доступ.
8. Порт PostgreSQL опубликован на хосте для разработки. В постоянном окружении его следует закрыть от внешней сети.
9. Контактные данные Checko могут отсутствовать или быть устаревшими; наличие email не подтверждает релевантность или согласие на рекламу.
10. Нет региональных ограничений и скоринга: релевантность сейчас определяется целевыми ОКВЭД и требует оценки выборки человеком.
11. Git-репозиторий и история доступны; рабочие изменения текущей итерации пока не закоммичены.
12. В рабочей папке присутствует отдельный файл с учётными данными. Его нельзя включать в будущий Git-репозиторий; рекомендуется перенести его за пределы проекта и добавить явное правило игнорирования.

## Опробованные подходы, которые не сработали

- Первый Docker build backend завершился ошибкой из-за тайм-аута доступа к `pypi.org` при установке build dependencies. Повторная сборка при восстановившемся соединении прошла успешно; код приложения причиной ошибки не был.
- Открытие `0.0.0.0:8000` как пользовательского интерфейса приводило к `Not Found`. Это адрес прослушивания backend, а не frontend URL.
- Старый локальный Uvicorn на `127.0.0.1:8000` перехватывал локальные проверки и показывал demo/SQLite-состояние вместо Docker. Процесс остановлен; текущий порт обслуживает Docker-backend с Checko и PostgreSQL.
- Первый live-запуск остановился на карточке с повторяющимся дополнительным ОКВЭД: PostgreSQL отклонил дубль, а SQLAlchemy-сессия не смогла сохранить финальный статус. Парсер и upsert теперь дедуплицируют коды, запись компании выполняется в savepoint, а прерванный запуск закрывается при старте backend.

## Следующие шаги

### Качество и надёжность discovery

1. Сохранить для каждого кандидата исходный ОКВЭД-запрос, по которому он найден, и собирать результат/ошибку отдельно по каждому коду.
2. Добавить ограниченный retry/backoff для временных ошибок соединения Checko.
3. Показывать в интерфейсе предупреждение, если `completed`-запуск содержит `errors_count > 0`.
4. Довести выборку до 20–50 компаний малыми порциями и вручную отметить релевантность, наличие email и шум по каждому исходному ОКВЭД.
5. После оценки скорректировать список кодов, режим поиска по основным/дополнительным ОКВЭД и их приоритеты.
6. Увеличивать лимит постепенно с учётом тарифа и дневного лимита Checko.

### Инфраструктура после подтверждения качества

1. Добавить Alembic и первую зафиксированную миграцию.
2. Перенести долговременные поиски в очередь задач с восстановлением после рестарта.
3. Добавить внутреннюю авторизацию и закрыть прямой внешний доступ к PostgreSQL/backend.
4. Перенести файл с учётными данными за пределы проекта, расширить `.gitignore`, затем инициализировать Git и создать первый baseline commit.

Email outreach проектировать только после подтверждения качества discovery-выборки и стабильности хранения/дедупликации.
