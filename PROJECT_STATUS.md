## Текущие цели

1. Завершить эксплуатационную проверку исправлений SMTP/IMAP на разрешённом сетевом
   маршруте, не меняя VPN без отдельного решения пользователя.
2. Восстановить доступ к заблокированному Mail.ru-аккаунту, затем проверить его пароль
   приложения непосредственно из FuelLead без отправки письма.
3. Только после успешной проверки SMTP вручную продолжить приостановленную кампанию и
   проконтролировать первые отправки, копии в «Отправленных» и возвраты.
4. Зафиксировать текущий незакоммиченный этап в Git после повторной runtime-проверки.

Безопасное состояние сохранено: в локальном `.env` и `.env.example`
`OUTREACH_AUTOMATIC_SEND_ENABLED=false`. Пароли ящиков вводятся только пользователем в
FuelLead, шифруются backend и не должны попадать в Git, логи, этот документ или чат.

- Разобрана повторная почтовая авария и отделены независимые причины: ошибка

## Ключевые технические решения

- Состояние доставки и здоровье отправителя независимы. Ошибка конкретного получателя
  не ухудшает здоровье ящика; доказанная ошибка ящика не завершает доставку получателя.
- `accepted` означает только SMTP DATA/250. Ошибка сохранения копии через IMAP не меняет
  `accepted` и не вызывает повторную отправку.
- Проблемы до приёма сообщения допускают повтор через другой ящик; проблемы после DATA
  без достоверного ответа считаются неопределёнными и требуют решения оператора.
- SMTP и IMAP имеют раздельные статусы. Успешный IMAP-вход не доказывает возможность
  SMTP-отправки и наоборот.
- Результаты сетевых и почтовых проверок применяются только при совпадении ревизии
  аккаунта/пароля; для IMAP дополнительно проверяется namespace `UIDVALIDITY`.
- Кампания не возобновляется автоматически после ручной паузы. Если исправных ящиков
  нет, она остаётся на паузе с понятной причиной, а получатели сохраняются.
- Диагностика не выводит пароли, AUTH payload, полный текст писем и произвольные ответы
  провайдера. Секреты по-прежнему шифруются Fernet-ключом из локального окружения.

## Известные проблемы и ограничения

- SMTP через сохранённый маршрут v2RayTun: TCP устанавливался, но TLS на 465 зависал и
  с macOS, и из Docker. Порт 587 через тот же маршрут также не дал приветствие. Код
  приложения не может устранить этот внешний сетевой блок.
- Прямой диагностический маршрут через Wi-Fi получал SMTP-приветствие быстро, но
  системный маршрут не менялся по просьбе пользователя. Любое изменение VPN/маршрута
  требует нового явного решения.
- Один аккаунт (`artel.work@mail.ru`, ящик №2 в последнем снимке) заблокирован Mail.ru
  из-за подозрительной активности; он приостановлен в FuelLead. Сначала нужен ручной
  возврат доступа на сайте Mail.ru, затем новый пароль приложения с подходящими правами.
- Live SMTP AUTH после последних исправлений, новая реальная отправка, попадание во
  «Входящие» и новый реальный DSN через IMAP не подтверждены.
- Последний снимок кампании №63: `paused`, круг 16, `366 queued`, `103 accepted`,
  `19 bounced`, `12 failed`. Это не текущая гарантия: после запуска Docker состояние
  нужно перечитать. Нельзя автоматически переотправлять старые `failed`/`uncertain`.
- Mail.ru применяет собственные ограничения и защиту. Для регулярной массовой работы
  личные ящики остаются эксплуатационным риском; переход на доменную почту/Postmaster —
  отдельное архитектурное решение, не входившее в этап.

## Опробованные, но не сработавшие или отброшенные подходы

- Пересборка контейнеров и успешные тесты не восстановили live SMTP: причина текущего
  тайм-аута находится до AUTH, в сетевом маршруте.
- Проверка альтернативного SMTP-порта 587 через тот же VPN не обошла блокировку.
- Замена пароля не является исправлением TLS-тайм-аута: пароль ещё не используется на
  этапе зависшего handshake. Сначала нужна успешная `--network`-диагностика.
- Прежняя логика автоматически считала временно ошибочный ящик исправным после номера
  круга. Это было недостоверно и заменено обязательной SMTP-проверкой.
- Прежняя классификация любого DATA 550 как ошибки отправителя отключала ящики из-за
  несуществующего получателя. Решение заменено анализом SMTP-этапа, enhanced code и
  доказательства того, к какому адресу относится отказ.
- Повтор заведомо не принятого письма через тот же сломанный ящик приводил к потере
  получателя в `failed`; теперь получатель остаётся в общей очереди для другого ящика.

## Следующие шаги

1. Запустить Docker Desktop. До любых сетевых проверок подтвердить, что автоматическая
   отправка выключена, кампания не работает и нет активной SMTP-попытки.
2. Сделать свежую резервную копию рабочей PostgreSQL, затем пересобрать backend,
   imap-worker и frontend; проверить применение `20260911_imap_uidvalidity`.
3. Повторить в контейнере 352 backend-теста, frontend build, health/API smoke и сверку
   основных счётчиков/состояния кампании с последним снимком. Не отправлять письма.
4. После согласования допустимого маршрута выполнить
   `docker compose exec -T backend python -m app.commands.check_mailboxes --network`.
   Все используемые SMTP/IMAP endpoints должны пройти DNS → TCP → TLS → greeting.
5. Восстановить заблокированный аккаунт на сайте Mail.ru. Пользователь должен сам
   сохранить новый пароль приложения в FuelLead; для включённого IMAP нужен полный
   доступ к Почте.
6. Выполнить
   `docker compose exec -T backend python -m app.commands.check_mailboxes --verify`.
   Это проверяет AUTH и обновляет статусы, но не отправляет письмо. Убедиться, что
   нужные SMTP-ящики имеют `verified`, а ручная пауза кампании сохранилась.
7. Только с отдельного подтверждения отправить одно тестовое письмо на явно указанный
   адрес. Проверить SMTP DATA/250, Message-ID, копию в «Отправленных», получение во
   «Входящих» и последующий DSN-сценарий.
8. Вручную продолжить кампанию №63. Проконтролировать первые получатели/ящики и убедиться,
   что ошибки получателя не блокируют отправителя, а ошибка отправителя сохраняет адрес
   в очереди. Не разрешать `uncertain` без ручной проверки фактической доставки.
9. После runtime-приёмки просмотреть diff, закоммитить текущий этап единым осмысленным
   коммитом, отправить в remote и отдельно зафиксировать факт целевого развёртывания.
