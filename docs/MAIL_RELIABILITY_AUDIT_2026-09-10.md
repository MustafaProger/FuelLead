## Повторная диагностика

Команда не отправляет писем и не выводит пароли. С `--verify` проверяет подключения и обновляет их статусы:

```sh
docker compose exec -T backend python -m app.commands.check_mailboxes --verify
```

Без `--verify` показывает сохранённые статусы и возможность расшифровать пароль:

```sh
docker compose exec -T backend python -m app.commands.check_mailboxes
```

При сетевой временной ошибке повторная фоновая проверка планируется через 5 минут и выполняется imap-worker на следующем цикле. Активные и приостановленные кампании не обходятся фоновым восстановлением. Постоянный отказ авторизации, ошибка ключа шифрования, сертификата или отказ провайдера требуют явной проверки/устранения причины.

## Что зависит от Mail.ru

Обещать отсутствие всех будущих сбоев нельзя. Mail.ru может ограничивать частоту и отправляющий ящик, отклонять содержание письма, менять антиспам-решение; получатель может отсутствовать или иметь переполненную квоту. Локальный дневной лимит не гарантирует разрешение провайдера на такой объём.

Если повторится 550, теперь нужно смотреть сохранённый полный безопасный ответ, а не сразу менять пароль. При 535 проверяются доступ по IMAP/SMTP и действительность пароля приложения. При ошибке расшифровки восстанавливается прежний ключ FuelLead в обоих процессах; менять пароль на сайте Mail.ru из-за этой ошибки не нужно.

Официальная справка: [ошибки Mail.ru и ограничения отправки](https://help.mail.ru/developers/errors/), [настройки доступа внешних сервисов](https://help.mail.ru/mail/security/protection/settings/), [передача bytes и SMTP-формат в Python](https://docs.python.org/3/library/smtplib.html).
