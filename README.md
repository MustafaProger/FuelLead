# FuelLead MVP

Внутреннее приложение для поиска потенциальных клиентов топливных карт по ОКВЭД, получения карточек компаний через переключаемого провайдера, хранения данных в PostgreSQL и выгрузки в Excel.

## Что уже реализовано

- discovery-провайдеры `checko`, `okvedo`, `dadata`, `api_fns`, `combined` и `demo`;
- последовательный запуск обоих платных провайдеров одной кнопкой: сначала Checko, затем API-ФНС;
- поиск действующих ЮЛ через API-ФНС по основному ОКВЭД и через Checko по основным и дополнительным ОКВЭД (`codes=all`);
- проверка действующего статуса компании;
- получение названия, ИНН, ОГРН, основного и дополнительных ОКВЭД;
- получение email и телефонов из карточки выбранного провайдера;
- ручное добавление телефона, WhatsApp и Telegram в карточке компании;
- удаление компании с сохранением ИНН во внутреннем стоп-листе, чтобы поиск не вернул её обратно;
- PostgreSQL как основная база, подключение только через переменные окружения;
- дедупликация компаний по ИНН и email внутри компании;
- продолжение поиска со следующей позиции провайдера для каждой пары «ОКВЭД + регион»;
- даты первого обнаружения, последней проверки и последнего обновления;
- понятные статусы воронки: `new`, `sent`, `answered`, `interested`, `customer`, `rejected`,
  а также системный `error` для ошибок отправки;
- история обнаружения, обновлений, новых email и смен статуса;
- фильтры по статусу, наличию email, категории деятельности, дате, названию и ИНН;
- адаптивный React-интерфейс;
- внутренняя авторизация с постоянной подписанной сессией в `HttpOnly` cookie;
- отдельный дашборд с воронкой, активностью поиска и последними компаниями;
- сохраняемый шаблон письма с переменными компании и текущей даты;
- персональный предпросмотр и редактирование письма выбранной компании;
- безопасное подключение нескольких ящиков Mail.ru с зашифрованными паролями внешних приложений;
- последовательный SMTP-планировщик по ящикам, пачкам и кругам с сохраняемыми таймерами;
- снимок кампании, подтверждение запуска, пауза, необратимая остановка и ручное разрешение неопределённых отправок;
- глобальные email-исключения и IMAP-сборщик стандартных уведомлений о недоставке;
- экспорт текущей выборки в `.xlsx`;
- отдельный демонстрационный режим без внешних запросов.

Поиск сайтов и полноценные CRM-функции не включены. Новые кампании создаются только
вручную из интерфейса и не начинают отправку до отдельного подтверждения снимка.
Технические ограничения не отменяют требования к релевантности обращения и обработке
отказов получателей.

## Быстрый запуск через Docker

Требуются Docker Desktop и запущенный Docker Engine.

```bash
cd FuelLead
cp .env.example .env
docker compose up --build
```

После запуска откройте:

- интерфейс: `http://localhost:8080`;
- документация API: `http://localhost:8000/docs`;
- проверка backend: `http://localhost:8000/api/health`.

В `.env.example` выбран `DISCOVERY_PROVIDER=demo`, поэтому новый локальный запуск не делает внешних запросов. Это позволяет проверить весь интерфейс, PostgreSQL, статусы, историю, фильтры и экспорт без расхода лимитов.

Перед первым запуском задайте в локальном `.env` отдельные данные входа в FuelLead:

```dotenv
FUELLEAD_AUTH_EMAIL=operator@example.com
FUELLEAD_AUTH_PASSWORD=replace-with-a-strong-password
FUELLEAD_AUTH_SESSION_SECRET=replace-with-a-long-random-secret
FUELLEAD_AUTH_COOKIE_DAYS=3650
FUELLEAD_AUTH_COOKIE_SECURE=false
```

Пароль проверяется только backend и не включается во frontend-сборку. Для размещения
исключительно по HTTPS установите `FUELLEAD_AUTH_COOKIE_SECURE=true`. Вход сохраняется
на устройстве на 3650 дней и переживает перезапуски backend: повторная авторизация нужна
только после явного выхода, очистки cookies либо смены пароля/секрета сессии.

## Выбор discovery-провайдера

Для поиска через все настроенные источники укажите в локальном `.env`:

```dotenv
DISCOVERY_PROVIDER=combined
```

Кнопка «Запустить полный поиск» создаёт один фоновый проход (`search_scope=full`).
Он продолжает обработку с сохранённой позиции до лимита провайдера или конца выдачи
по заданным ОКВЭД в Москве и Московской области. Ограничения старой порции
`DISCOVERY_LIMIT_PER_CODE` и двух страниц на запрос в этом режиме не применяются.
Checko/Okvedo запрашивают страницы по 100 записей, API-ФНС — по 100, DaData — по 20.
Отсутствующие карточки DaData пропускаются, чтобы один ИНН не блокировал остальные.

Запросы идут последовательно с паузой 1,05 секунды. Временный `rate_limit` повторяется
до трёх раз с ожиданием 60/120/180 секунд (или больше, если Okvedo передал `Retry-After`).
Суточный лимит, неверный ключ и недоступность источника отображаются отдельно.
Интерфейс показывает текущий источник/страницу, число поисковых вызовов и запросов
карточек, добавленные компании и причины окончания этапов. Эти счётчики отражают
вызовы клиента, включая повторы после ограничения частоты; внутренние переключения
ключей Checko и служебные запросы статистики отдельно не учитываются.

Можно закрыть вкладку: поиск выполняет backend. При возвращении интерфейс восстанавливает
последний запуск. «Остановить поиск» завершает текущий запрос и сохраняет результат
с позицией продолжения. Повторное нажатие из другой вкладки возвращает уже активный запуск.
Для работы в фоне сервер и компьютер должны оставаться включёнными. После перезапуска
backend прерванный запуск помечается ошибкой; следующий запуск использует сохранённые курсоры.
Ежедневный запуск по расписанию не включён.

Последовательность источников:

1. Checko — с переключением между всеми настроенными ключами отдельно для поиска и карточек;
2. Okvedo — поиск по ОКВЭД и региону, затем карточки неизвестных ИНН;
3. DaData — подсказки по ОКВЭД и региону, затем карточки неизвестных ИНН;
4. API-ФНС — **только если каждый настроенный источник выше подтвердил исчерпание суточной квоты**.

Провайдер без ключа пропускается. Пустая выдача, завершение очередной порции поиска,
лимит одного запуска, неверный ключ, таймаут и минутное ограничение **не открывают**
резерв API-ФНС. Если хотя бы у одного основного источника исчерпание квоты не подтверждено,
API-ФНС не вызывается. Checko должен исчерпать все настроенные ключи; смесь исчерпанных
и отклонённых ключей не считается доказательством исчерпания. Для неоднозначной ошибки
DaData 403 дополнительно проверяется сегодняшний `remaining.suggestions` через статистику.
Если статистика недоступна, резерв остаётся закрыт.

Курсоры разделены по провайдеру, ОКВЭД и региону. Уже известные и исключённые ИНН
отсеиваются до запроса карточки. Частично найденные компании и позиция курсора
сохраняются при исчерпании квоты. Перед сохранением проверяются активность и текущий
регион компании (Москва или Московская область), а не префикс ИНН.

Режимы `checko`, `okvedo`, `dadata` выбирают отдельный источник; `demo` использует демонстрационные
данные. `auto` выбирает настроенные источники. `api_fns` при наличии основных источников
также переходит в `combined`, чтобы не обходить правило последнего резерва. Если настроен
только API-ФНС, он используется самостоятельно.

## Подключение Okvedo и DaData

Ключи задаются только в игнорируемом `.env` (значения в `.env.example` пустые):

```dotenv
OKVEDO_API_KEY=your-local-key
OKVEDO_BASE_URL=https://okvedo.ru/api/v1
OKVEDO_TIMEOUT_SECONDS=30
DADATA_API_KEY=your-local-key
DADATA_SECRET_KEY=your-local-secret
DADATA_BASE_URL=https://suggestions.dadata.ru/suggestions/api/4_1/rs
DADATA_TIMEOUT_SECONDS=30
```

Okvedo использует `GET /companies` с фильтрами `okved`, `region`, `status=active` и
параметрами `page`/`limit`, затем `GET /companies/{inn}`. Ключ передаётся заголовком
`X-Api-Key`. Явно помеченные низкой оценкой дозвона номера (`dial_score < 30`) пропускаются.
Документация: [методы и лимиты](https://okvedo.ru/integrations),
[OpenAPI](https://okvedo.ru/api/v1/docs).

DaData использует `POST /suggest/party` с фильтрами `type=LEGAL`, `status=ACTIVE`,
`okved`, `locations`, затем `POST /findById/party` с `branch_type=MAIN`.
Подсказки возвращают **до 20 компаний на сочетание ОКВЭД/региона без пагинации**:
это дополнительная ограниченная выборка, а не полная выгрузка реестра. Повторные запуски
продолжают обработку этой порции, но не гарантируют новые результаты после её завершения.
Телефоны, email и дополнительные сведения сохраняются, если доступны на тарифе.
Секретный ключ используется только для `GET https://dadata.ru/api/v2/stat/daily` после
403 и не передаётся в подсказки. Никакие платные методы стандартизации не вызываются.
Документация: [подсказки](https://dadata.ru/api/suggest/party/),
[карточки](https://dadata.ru/api/find-party/), [статистика](https://dadata.ru/api/stat/).

После изменения кода и `.env` пересоздайте backend и обновите frontend:

```bash
docker compose up -d --build --force-recreate backend frontend
```

## Подключение API-ФНС

Ключ хранится только в игнорируемом локальном `.env`:

```dotenv
DISCOVERY_PROVIDER=combined
API_FNS_KEY=your-local-key
API_FNS_BASE_URL=https://api-fns.ru/api
API_FNS_TIMEOUT_SECONDS=30
API_FNS_REQUIRE_PHONE=false
API_FNS_REQUIRE_EMAIL=false
API_FNS_MAX_SEARCH_REQUESTS_PER_RUN=5
API_FNS_MAX_EGR_REQUESTS_PER_RUN=5
```

API-ФНС ищет только по **основному ОКВЭД**. FuelLead передаёт `active`, `onlyul`, отдельный
`okved...` и отдельный `region77`/`region50`, продолжает поиск по страницам и повторно
проверяет регион полной карточки `egr` перед сохранением. Дополнительные ОКВЭД читаются
из карточки, но не используются как подтверждённый критерий поиска API-ФНС.

Фильтры `withphone` и `withemail` поддерживаются настройками
`API_FNS_REQUIRE_PHONE`/`API_FNS_REQUIRE_EMAIL`. По умолчанию они выключены, чтобы не
исключать организации без одного из типов контактов. Известные и исключённые ИНН
отсеиваются до лимитируемого запроса `egr`.

Пределы `API_FNS_MAX_SEARCH_REQUESTS_PER_RUN` и `API_FNS_MAX_EGR_REQUESTS_PER_RUN`
применяются только к явно запрошенному режиму `search_scope=batch`. Полный поиск из
интерфейса продолжает этап API-ФНС до ответа о лимите или конца доступной выдачи,
если выполнено условие подключения резерва. Количество запросов не равно количеству
новых компаний: поиск страниц и получение карточек расходуют отдельные вызовы.

Для ручной минимальной проверки выполните одну безопасную команду. Она печатает только
счётчики и выбранные поля, не выводит ключ или полный URL, и делает максимум один `search`
и один `egr` между двумя вызовами `stat`:

```bash
docker compose exec -T backend python -m app.commands.check_api_fns
```

Чтобы только посмотреть расход лимита без вызова `search` и `egr`, используйте:

```bash
docker compose exec -T backend python -m app.commands.check_api_fns --stat-only
```

При необходимости можно безопасно изменить только тестовые параметры:

```bash
docker compose exec -T backend python -m app.commands.check_api_fns --okved 49.41 --region 50
```

Официальная документация: [описание API](https://api-fns.ru/api_help),
[метод search](https://api-fns.ru/api/search), [метод egr](https://api-fns.ru/api/egr),
[метод stat](https://api-fns.ru/api/stat).

## Подключение Checko

Укажите ключ в локальном `.env`:

```dotenv
CHECKO_API_KEY=your-local-key
CHECKO_API_KEY_FALLBACKS=your-second-key,your-third-key
```

Ключи не передаются во frontend и не должны попадать в Git. При исчерпании суточного
лимита или отклонении текущего ключа backend повторяет тот же запрос со следующим ключом.
Если недоступны все настроенные ключи, поиск корректно останавливается с сохранением
уже полученных результатов. Интеграция использует официальные методы:

- `GET https://api.checko.ru/v2/search` с `by=okved`, `obj=org`, `active=true`, `codes=all`
  и отдельными запросами `region=77` (Москва), `region=50` (Московская область);
- `GET https://api.checko.ru/v2/company` по ИНН.

Перед сохранением backend повторно проверяет `Регион.Код` полной карточки. Компании
других регионов и карточки без кода региона в PostgreSQL не записываются.

Документация: [поиск](https://checko.ru/integration/api/search), [карточка организации](https://checko.ru/integration/api/company).

Размер первого поиска задаётся переменной:

```dotenv
DISCOVERY_LIMIT_PER_CODE=10
```

По каждому ОКВЭД лимит применяется отдельно к Москве и Московской области. Backend
сохраняет позицию каждого поиска в PostgreSQL, при следующем запуске переходит к следующим
результатам и не запрашивает повторно полные карточки уже известных ИНН. Перед увеличением
лимита оцените стоимость запросов и баланс выбранного провайдера.

Для проверки и удаления уже сохранённых компаний других регионов используйте безопасную
команду. Без `--apply` она только показывает план удаления:

```bash
docker compose exec backend python -m app.commands.prune_non_target_regions
docker compose exec backend python -m app.commands.prune_non_target_regions --apply
```

## Подключение ящиков Mail.ru

FuelLead использует `smtp.mail.ru:465` с SSL/TLS с момента подключения и, если IMAP
включён, `imap.mail.ru:993` с SSL/TLS. Логином служит полный адрес ящика, а секретом —
отдельный новый пароль внешнего приложения. Обычный пароль от Mail.ru использовать нельзя.

Сначала сгенерируйте ключ шифрования. Команда выводит ключ только в локальный терминал:

```bash
docker compose run --rm backend python -m app.commands.generate_mail_credentials_key
```

Скопируйте результат в игнорируемый Git файл `.env`:

```dotenv
MAIL_CREDENTIALS_ENCRYPTION_KEY=
OUTREACH_AUTOMATIC_SEND_ENABLED=false
```

В репозитории значение ключа не хранится. После изменения `.env` обязательно пересоздайте
backend и IMAP-worker — обычный `restart` не перечитывает переменные окружения:

```bash
docker compose up -d --build --force-recreate backend imap-worker
```

Затем откройте раздел «Почтовые ящики», добавьте три адреса и введите для каждого его
новый пароль внешнего приложения непосредственно в форму:

- `artel.work@mail.ru`;
- `mustafa.tojiev.2005@mail.ru`;
- `artel.office8@mail.ru`.

Пароль отправляется backend только при сохранении или замене, немедленно шифруется и не
возвращается через API. Frontend очищает поле после запроса, не сохраняет его в
`localStorage`/`sessionStorage` и показывает лишь признак «Пароль сохранён».

Кнопка «Проверить подключение» устанавливает SMTP SSL-соединение и выполняет авторизацию,
но не отправляет письмо. При включённом IMAP также проверяется IMAP SSL-авторизация.
«Отправить тестовое письмо» доступна отдельно: она отправляет ровно одно письмо на адрес,
который оператор вручную ввёл и подтвердил; компании из базы для этой проверки не
выбираются.

## Многопочтовая рассылка

Кнопка «Отправить письма» создаёт снимок темы, текста, активных получателей, проверенных
активных ящиков и настроек планировщика. Снимок нужно подтвердить в течение 10 минут.
Одновременно может работать только одна кампания.

Планировщик обрабатывает письма строго последовательно: одна пачка первого ящика, одна
пачка второго, одна пачка третьего, затем общий отдых и следующий круг. Интервалы между
письмами случайно выбираются в диапазоне 60–85 секунд, общий отдых — 77–93 минуты. Оба
таймера сохраняются в PostgreSQL и продолжают действовать после паузы или перезапуска.
Дневной лимит задаётся отдельно для каждого ящика. Размер пачки растёт от 5 до 12 только
после полностью успешных пачек без единой ошибки и сохраняется между кампаниями.

Перед каждым SMTP-вызовом повторно проверяются компания, её адрес и статус, отсутствие
предыдущей отправки и глобального исключения. Нарушение переводит запись в `suppressed`
без SMTP-вызова. Результат `accepted` означает только принятие SMTP-сервером после DATA;
он не подтверждает доставку или попадание во «Входящие».

Постоянный отказ адреса переводит письмо в `bounced` и добавляет адрес в глобальные
исключения. Периодический IMAP-worker разбирает стандартные DSN, сопоставляет поздние
возвраты по техническим заголовкам и Message-ID и идемпотентно меняет `accepted` на
`bounced`. Неопределённый результат после начала SMTP-попытки получает `uncertain`, не
повторяется автоматически и переводит кампанию в `interrupted` до ручного решения.

«Пауза» запрещает начинать новые попытки, сохраняя таймеры. «Остановить рассылку»
необратимо переводит оставшиеся `queued` в `cancelled`. Для запуска реальной кампании
после всех проверок используется только явное подтверждение в интерфейсе; флаг
`OUTREACH_AUTOMATIC_SEND_ENABLED` должен оставаться `false`.

Каждое письмо получает стандартный `Message-ID`, технические заголовки сопоставления,
`List-Unsubscribe` через `mailto:` и видимый текст отказа. Низкая скорость снижает риск
технических ограничений, но не гарантирует доставку и не делает нежелательную рассылку
допустимой.

Доступные переменные шаблона:

- `{{company_name}}` — название компании;
- `{{date}}` — сегодняшняя дата в часовом поясе приложения;
- `{{inn}}` — ИНН;
- `{{primary_okved}}` — основной ОКВЭД;
- `{{email}}` — выбранный email получателя.

## Настройка PostgreSQL

Перед постоянным использованием замените демонстрационный пароль одновременно в `POSTGRES_PASSWORD` и `DATABASE_URL`:

```dotenv
POSTGRES_DB=fuellead
POSTGRES_USER=fuellead
POSTGRES_PASSWORD=replace-with-a-strong-password
DATABASE_URL=postgresql+psycopg://fuellead:replace-with-a-strong-password@db:5432/fuellead
```

Данные PostgreSQL сохраняются в Docker volume `fuellead_postgres_data` и не исчезают после перезапуска контейнеров.

## Локальная разработка без Docker

Backend по умолчанию использует локальный SQLite только как удобный режим разработки и автоматических тестов. Рабочая конфигурация Docker использует PostgreSQL.

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -e '.[test]'
.venv/bin/uvicorn app.main:app --reload
```

Во втором терминале:

```bash
cd frontend
npm install
npm run dev
```

Откройте `http://localhost:5173`.

## Основные API

- `POST /api/auth/login` — вход и создание защищённой сессии;
- `GET /api/auth/session` — проверка текущей сессии;
- `POST /api/auth/logout` — выход и отзыв текущей сессии;
- `GET /api/companies` — список, статистика и фильтры;
- `GET /api/companies/{id}` — карточка, дополнительные ОКВЭД и история;
- `PATCH /api/companies/{id}/status` — смена статуса;
- `POST /api/companies/{id}/contacts` — добавление телефона, WhatsApp или Telegram;
- `DELETE /api/companies/{id}/contacts/{contact_id}` — удаление ручного контакта;
- `DELETE /api/companies/{id}` — удаление компании и добавление ИНН в стоп-лист;
- `GET /api/dashboard` — показатели, воронка, активность и последние компании;
- `GET /api/email-template` — текущий основной шаблон и список переменных;
- `PUT /api/email-template` — сохранение основного шаблона;
- `POST /api/email-template/preview` — персонализация шаблона для выбранной компании;
- `POST /api/companies/{id}/send-email` — одиночная отправка проверенного письма;
- `GET|POST /api/sender-accounts` — безопасное управление почтовыми ящиками;
- `PATCH|DELETE /api/sender-accounts/{id}` — изменение, пауза и подтверждённое удаление ящика;
- `POST /api/sender-accounts/{id}/verify` — SMTP/IMAP-проверка без письма;
- `POST /api/sender-accounts/{id}/test-email` — одно подтверждённое тестовое письмо;
- `GET|POST /api/email-suppressions` — просмотр и ручное добавление исключений;
- `POST /api/email-suppressions/{id}/lift` — осторожное ручное снятие исключения;
- `POST /api/outreach/preflight` — создание снимка кампании на 10 минут;
- `POST /api/outreach/start` — подтверждение и запуск снимка;
- `POST /api/outreach/{id}/pause|resume|stop` — управление кампанией;
- `POST /api/outreach/{id}/deliveries/{delivery_id}/resolve` — ручное решение `uncertain`;
- `GET /api/search-runs/latest` — восстановление последнего поиска;
- `POST /api/search-runs/{id}/stop` — остановка после текущего запроса;
- `POST /api/search-runs` — запуск поиска;
- `GET /api/search-runs/{id}` — состояние поиска;
- `GET /api/export.xlsx` — Excel-выгрузка.
